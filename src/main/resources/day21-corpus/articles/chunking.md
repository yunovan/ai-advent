# Чанкинг документов для индексации

Чанкинг — это разбиение большого документа на мелкие фрагменты, каждому из которых
затем сопоставляется вектор-эмбеддинг. От того, как нарезан текст, напрямую
зависит качество поиска по индексу: слишком крупные чанки теряют точность,
слишком мелкие — теряют смысл.

## Зачем нужны чанки

Модели эмбеддингов, как и языковые модели, имеют ограниченный контекст. Целый
README на тысячи строк превратить в один вектор нельзя — семантика перемешается, а
поиск перестанет различать, в какой секции документа находится ответ. Индексация
по чанкам решает две задачи:

- единица хранения в индексе совпадает с единицей поиска; по найденному чанку мы
  всегда можем показать источник, заголовок и раздел документа;
- эмбеддинг чанка отражает локальную тему фрагмента, а не смесь всех тем сразу;
  запрос «косинусная близость» попадает в нужный фрагмент, а не в усреднённую
  сумму всего документа.

## Стратегия по фиксированному размеру

Самая простая стратегия: текст режется на окна фиксированной длины с небольшим
перекрытием. Алгоритм движется по тексту, выравнивая границы по пробелам, чтобы не
разрезать слово пополам. Перекрытие между соседними окнами оставляет каждую мысль,
попавшую на границу, хотя бы в одном целом чанке.

Достоинства:

- предсказуемый размер чанков, одинаковая стоимость эмбеддингов;
- простой код, работающий с любым форматом текста без разбора структуры.

Недостатки:

- границы чанков не совпадают со смысловыми границами; предложение, попавшее на
  стык окон, теряется наполовину;
- заголовки и списки могут оказаться в соседнем чанке, и тогда извлекать из чанка
  «откуда это» можно только подсчётом расстояний.

Хорошая новость в том, что метаданные чанка (source, title, section) можно
обогатить даже при фиксированной нарезке: перед построением индекса сканируем
исходный текст и запоминаем позиции заголовков, а затем каждому окну присваиваем
ближайший предыдущий заголовок как его секцию.

## Стратегия по структуре документа

Вторая стратегия уважает структуру исходного формата. Для markdown границами
чанков становятся заголовки и параграфы: каждый заголовок открывает новый раздел,
а внутри раздела текст собирается параграфами до целевого размера. Для кода —
объявления классов, интерфейсов и методов. Для простого текста — параграфы,
разделённые пустыми строками.

Достоинства:

- секция каждого чанка известна заранее и соответствует реальному разделу
  документа; ответ на запрос сразу приходит с контекстом «из какого раздела»;
- предложения и абзацы не разрываются, поэтому смысловые единицы остаются
  целыми;
- по структуре удобно объяснять результат: найден чанк `…/embeddings.md` в
  разделе «Метрики близости».

Недостатки:

- требует понимания формата документа; для неизвестного формата работает
  вырожденный вариант «по параграфам»;
- размер чанков менее равномерен, если в корпусе встречаются очень короткие или
  очень длинные разделы.

## Метрики сравнения стратегий

Чтобы сравнить стратегии честно, нужны измеримые величины. Обычно смотрят на:

- средний размер чанка, минимальный и максимальный, стандартное отклонение;
- коэффициент вариации (CV) — разброс размера относительно среднего; чем меньше,
  тем ровнее нарезка;
- покрытие пробных запросов: берём набор вопросов с известным правильным ответом
  и проверяем, попадает ли правильный фрагмент в топ результатов поиска.

Покрытие проб — главный показатель качества, потому что он измеряет результат
конечного пользователя: поиск по индексу. CV второстепенен, но полезен для
диагностики.

## Выводы

Нет единственной правильной стратегии. Для структурированных форматов — markdown,
код, документы с заголовками — нарезка по структуре обычно точнее, потому что
чанки соответствуют логическим блокам текста. Для сырого текста без структуры
фиксированный размер остаётся надёжным выбором. Лучшее решение для любого
пайплайна — построить индекс обеими стратегиями и выбрать по метрикам на реальных
запросах.
